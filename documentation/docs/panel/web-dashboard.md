# Web dashboard (`asdd_tools/`)

`asdd_tools/` is a **single, self-contained HTML page** (`index.html`) that
renders your spec pipeline in the browser. It is **read-only**: it never writes
to disk and exposes no write endpoint. It simply fetches the generated JSON and
the spec Markdown and displays them.

## File layout

```
asdd_tools/
  config.json        ← project configuration (this is what you edit)
  index.html         ← the dashboard itself (do not edit)
  specs.json         ← generated by scripts/gen-specs-json.sh
  stack.json         ← generated: active + available stacks (for the selector)
  stacks/            ← technology profiles for the QA gate (one .json per stack)
    php.json
    node.json
    dotnet.json
    java.json
  running.json       ← live state of in-flight agents (managed by hooks, not versioned)
  specs/             ← directory served with the spec .md files
                       (usually a symlink to ../specs)
```

:::note Generated vs. hand-edited
You only ever edit `config.json` and the `stacks/*.json` profiles. `specs.json`,
`stack.json` and `running.json` are produced by the tooling.
:::

## Configuration — `config.json`

```json
{
  "project_name": "my-project",
  "specs_dir":    "../specs",
  "output_json":  "specs.json",
  "stack":        "php",
  "states":       [ /* … see below … */ ]
}
```

| Field | Description | Default |
|---|---|---|
| `project_name` | Name shown in the dashboard header. | — |
| `specs_dir` | Path to the specs directory, **relative to `asdd_tools/`**. | `../specs` |
| `output_json` | Name of the generated JSON, inside `asdd_tools/`. | `specs.json` |
| `stack` | Id of the technology profile (`stacks/<id>.json`) used by the QA gate. | — |
| `states` | The pipeline stages (dynamic). See [Customizing the pipeline states](#customizing-the-pipeline-states). | the standard 3-stage ASDD workflow |

The `stack` field is set with the wizard, not by hand — see
[Stacks & the QA gate](./stacks-and-qa.md).

## Customizing the pipeline states

The pipeline stages are **not hard-coded**. They are defined by the optional
`states` array in `config.json`. [`gen-specs-json.sh`](./scripts.md#gen-specs-jsonsh)
copies this array into `asdd_tools/stack.json`, and **both** surfaces — the web
dashboard and the [Claude Code plugin](./claude-code-plugin.md) — build their
pipeline, filters, counts, kanban columns and colours from it. Change the states,
regenerate, and the whole UI follows.

```json
"states": [
  { "id": "draft",       "label": "Draft",       "color": "#6272a4" },
  { "id": "approved",    "label": "Approved",    "color": "#ffb86c",
    "gates": [{ "label": "Validation", "note": "M · L" }] },
  { "id": "implemented", "label": "Implemented", "color": "#50fa7b",
    "gates": [{ "label": "Tests · check.sh", "note": "all" },
              { "label": "Sec · A11y", "note": "L" }] }
]
```

| Key | What it is |
|---|---|
| `id` | The literal value that appears in each spec's `estado` frontmatter field. Specs are grouped into this stage. |
| `label` | The name shown in the UI (e.g. `Draft`). |
| `color` | Hex colour for the stage. Each stage gets its colour from this value (built-in Spanish ids such as `borrador` also have extra hand-tuned styling). |
| `gates` | *(optional)* Quality gates drawn **before** this stage in the pipeline diagram. Each is `{ "label": "…", "note": "…" }`. |

The **order of the array is the order of the pipeline**. To change the workflow —
rename a stage, recolour it, add a `review` or `blocked` stage, or remove one —
edit this array and run `bash scripts/gen-specs-json.sh`. Nothing in `index.html`,
the plugin or the scripts needs to change.

:::note `id` must match your spec frontmatter
`id` is matched against the raw `estado` value in each spec's frontmatter, which
is free text. The defaults are `draft` / `approved` / `implemented`; `label` is
what the reader sees. Use whatever ids your specs actually contain — if your specs
write `estado: borrador`, set the id to `borrador`.
:::

## What the dashboard shows

- A header with the project name and a badge for the **active stack**.
- The **pipeline diagram**: `Draft → Approved → Implemented` with a live count in
  each stage (the stages are configurable — see
  [the pipeline states](./overview.md#the-pipeline-states)).
- **Filter chips** by state (draft / approved / implemented) and by level
  (`S` / `M` / `L`).
- A **card per spec** with its id, version, type, level, the quality gates it has
  cleared (`✓ val`, `✓ qa`, `✓ seg`, `✓ a11y`), a progress track and — when
  expanded — the per-document report summary (date, version, result, findings).
- Specs with **unresolved blocking findings** are flagged in red.

## Serving the dashboard

The page references **absolute paths** (`/asdd_tools/specs.json`, …), so it must
be served with `/asdd_tools/` resolving from the **server root**. Opening
`index.html` directly with `file://` will **not** work — the browser blocks the
`fetch` calls.

Any static HTTP server works. Which one to use depends on the project:

- **Web project** (already served by Apache/nginx): reuse that web server — add an
  alias or virtual host (below). The panel is served next to your app.
- **Non-web project** (a CLI, library, or service with no web server): you do
  **not** need Apache or a virtual host. Start the bundled **Node** server — it
  has no dependencies and serves the panel on its own.

### Apache / virtual host (web projects)

```apache
Alias /asdd_tools /path/to/your/project/asdd_tools
<Directory /path/to/your/project/asdd_tools>
    Options -Indexes
    AllowOverride None
    Require all granted
</Directory>
```

Then open `http://your-project.local/asdd_tools/`.

### Node (no dependencies)

A zero-dependency Node server ships with the tooling. Run it from the project
root:

```bash
node scripts/serve-panel.mjs          # port 8777, opens your browser
node scripts/serve-panel.mjs 9000     # a different port
node scripts/serve-panel.mjs --no-open
```

It serves the project root, redirects `/` to the panel and guards against path
traversal. See [`serve-panel.mjs`](./scripts.md#serve-panelmjs).

### Python (one-liner)

```bash
# from the project root (so /asdd_tools/... resolves)
python3 -m http.server 8777
# then open http://localhost:8777/asdd_tools/index.html
```

## Security

- The dashboard is **read-only**: no disk writes, no write endpoint.
- The `stacks/*.json` profiles contain commands that the QA runner executes —
  version them, review them as code, and do not let the web server user
  (e.g. `www-data`) have write access to `asdd_tools/`.
- Secrets and runtime state (`.api-key`, `running.json`, `.running.stack`) must
  never be committed; they are listed in `.gitignore`.
